# Event Database Schema Specification

**Project:** Generalized RahNegar platform  
**Document status:** Target database architecture  
**Database:** SQLite, fully offline  
**Source basis:** `docs/legacy-event-subsystem-audit.md` and `docs/event-subsystem-architecture-specification.md`  
**Scope:** Logical and physical design requirements for Events, EventAudit, integrity constraints, indexes, ownership, deletion, migration, and finalized-report consistency  
**Out of scope:** Executable SQL, migration scripts, production code, and authorization to alter legacy databases

## 1. Executive overview

The legacy `tbl_events` table cannot be reused directly as the target Event store. It has an autoincrement row id but the application does not preserve that identity during editing: a daily edit deletes all Events for the date and inserts replacements. It stores Station ownership only implicitly, stores Unit/type/time as unconstrained text, permits duplicate timestamps for the same Unit, has no foreign keys to Station or Unit, and has no audit history. The database accepts invalid dates, malformed times, unsupported Event types, and Unit values that do not belong to the active Station. Correctness therefore depends on one UI workflow, while other callers and direct writes can bypass it.

The new schema provides five guarantees:

1. **Stable identity.** Every Event has an immutable identifier that survives edits and is used by commands, audit records, concurrency checks, and reports.
2. **Auditability.** Every accepted ADD, EDIT, and DELETE creates an append-only EventAudit row in the same transaction as the Event mutation. Old and new canonical values remain recoverable.
3. **Chain-validation support.** Station/Unit ownership and chronological indexes allow the application to load and replay the complete Event chain for every affected Unit from its Trusted Runtime Baseline.
4. **Runtime reconstruction.** Canonical date, minute time, and derived chronological key allow deterministic physical runtime, ESD adjustment, RuntimeAfterOH, ServiceDays, and LongestRun projection. Events remain the only runtime authority.
5. **Database-level protection.** Foreign keys, checks, unique active-Event timestamp rules, append-only audit policy, and finalized-period transaction checks provide defense in depth below the UI.

The database cannot express the approved state machine or complete-chain validity as ordinary row constraints. Those rules remain mandatory in the transactional domain command handler. Schema constraints reject structurally impossible rows and races; they do not replace reconstruction from the Trusted Runtime Baseline or actionable Persian validation messages.

## 2. Events table design

### 2.1 Table purpose

`Events` stores the current authoritative set of operational Events. One active row represents one accepted state transition for one Unit at one user-entered minute. The table does not store calculated runtime totals. Runtime is a projection from the Trusted Runtime Baseline plus active Events.

The selected deletion strategy is a retained tombstone. Four supporting fields—`IsDeleted`, `DeletedAt`, `DeletedBy`, and `RowVersion`—are included in addition to the required domain fields. Section 11 explains this decision.

### 2.2 Complete field specification

| Name | SQLite data type | Nullability | Default behavior | Constraints | Purpose |
|---|---|---|---|---|---|
| `EventId` | `TEXT` | Required | Generated by the application before insert; no database auto-number default | Primary key; canonical 26-character ULID text; immutable; binary/case-stable collation | Stable Event identity across edit, delete/tombstone, audit, reporting, and migration provenance. |
| `StationId` | `TEXT` | Required | None; supplied from trusted Station context | Foreign key to `Stations(StationId)`; immutable; must agree with Unit ownership | Explicit Station isolation. Prevents an Event from being interpreted under the wrong station profile. |
| `UnitId` | `TEXT` | Required | None | Composite foreign key with `StationId` to Units ownership key; nonempty; editable only through validated command | Unit whose state changes. Complete chains and runtime are partitioned by Unit. |
| `EventType` | `TEXT` | Required | None | Exact canonical value in `START`, `NSD`, `ESD`, `OH`; ordinal/binary comparison; no aliases | Closed operational transition type. |
| `EventDate` | `INTEGER` | Required | None | Eight-digit Persian `yyyyMMdd` candidate range plus application calendar validation; must be at/after baseline/data-start boundary | Persian operating date used for UI conventions, sequential-day policy, finalized Persian month checks, and daily queries. |
| `EventTime` | `INTEGER` | Required | None | Minute-of-day from `0` through `1439`; no seconds | Canonical operator-entered local time. Display formatting derives `HH:mm`. |
| `EventDateTime` | `INTEGER` | Required | Derived by application; ordinary callers cannot choose it independently | Canonical local chronological minute key; consistent with EventDate/EventTime; immutable only when date/time are unchanged | Fast deterministic sorting, uniqueness, chain range queries, and runtime interval arithmetic. |
| `Remark` | `TEXT` | Optional | `NULL` when no remark | Unicode; explicit maximum selected by product policy; empty input normalized to NULL; overflow rejects, never truncates | Operator context. Does not affect state or runtime. |
| `CreatedAt` | `TEXT` | Required | Generated by trusted application clock | Canonical UTC ISO-8601 with fixed fractional-second policy and `Z`; immutable | When the database record was created, distinct from operational EventDateTime. |
| `CreatedBy` | `TEXT` | Required | Supplied from authenticated local user context | Foreign key to user/account identity when that table is retained; immutable; nonempty | Actor who created the Event. |
| `UpdatedAt` | `TEXT` | Optional | `NULL` at creation | Canonical UTC ISO-8601; set only by accepted Edit; must not precede CreatedAt | Most recent accepted content edit time and human-readable concurrency evidence. |
| `IsDeleted` | `INTEGER` | Required | `0` | Boolean check: `0` or `1`; changed only by Delete command; active queries require `0` | Tombstone marker. Deleted Events leave authoritative active chains without losing identity/audit referential integrity. |
| `DeletedAt` | `TEXT` | Optional | `NULL` | Required exactly when IsDeleted = 1; canonical UTC; must not precede CreatedAt | Commit time of accepted Delete. |
| `DeletedBy` | `TEXT` | Optional | `NULL` | Required exactly when IsDeleted = 1; user identity reference where supported | Actor who deleted the Event. EventAudit remains the detailed source of reason and old value. |
| `RowVersion` | `INTEGER` | Required | `1` | Positive integer; incremented exactly once per accepted Edit/Delete | Optimistic-concurrency token preventing stale Edit/Delete from overwriting a newer mutation. |

### 2.3 Primary key and identity generation

`EventId` uses an application-generated ULID stored as canonical uppercase 26-character `TEXT`. ULID is selected instead of SQLite `INTEGER PRIMARY KEY AUTOINCREMENT` because it is stable before insertion, works across offline databases and controlled migrations without id collisions, sorts approximately by creation time for diagnostics, and does not expose row order as business chronology. Event chronology always uses `EventDateTime`, not EventId.

Generation occurs inside the application command boundary immediately before a validated Add is persisted. The database validates canonical shape and primary-key uniqueness. Imported legacy rows receive new ULIDs while their legacy database/source id is retained in migration provenance or audit snapshot; legacy ids are not reused as global Event identity.

The ULID generator must be cryptographically or statistically collision-safe for offline use and injectable in tests. A collision is an insert failure and transaction rollback, not an instruction to overwrite an existing row.

### 2.4 Field mutability

**Immutable after Add:**

- `EventId`;
- `StationId`;
- `CreatedAt`;
- `CreatedBy`.

**Editable only through EditEventCommand:**

- `UnitId`;
- `EventType`;
- `EventDate`;
- `EventTime`;
- `Remark`.

When EventDate or EventTime changes, `EventDateTime` is recomputed in the same update. `UpdatedAt` and `RowVersion` change on every accepted Edit. A Unit change validates both the old and new Unit chains.

**Delete-controlled fields:** `IsDeleted`, `DeletedAt`, `DeletedBy`, and `RowVersion`. Tombstoned rows cannot be edited or deleted a second time through normal commands. Undelete is not part of the approved command set; a future restore feature requires an explicit command, complete-chain validation, audit action, and architecture decision.

### 2.5 Derived fields

`EventDateTime` is derived from EventDate and EventTime by the centralized Persian date/time value service. It is persisted because it is used heavily for sorting, uniqueness, full-chain range scans, runtime interval arithmetic, and index selectivity. It is not accepted independently from UI/import DTOs.

SQLite has no built-in Persian-calendar conversion capable of proving full equivalence between EventDate and EventDateTime. Consistency is guaranteed by:

- one application conversion implementation used by all commands and migration tooling;
- transaction handler recomputation on every Add/Edit;
- structural database checks on all three fields;
- an arithmetic consistency check between EventTime and the minute component of EventDateTime where the selected epoch representation permits it;
- automated round-trip validation;
- migration and maintenance integrity scans that recompute and compare every row.

## 3. EventType storage design

### 3.1 Canonical values

The only stored values are:

- `START`
- `NSD`
- `ESD`
- `OH`

Storage is uppercase ASCII with exact binary/ordinal comparison. Leading/trailing spaces, periods, localized aliases, mixed case, `Start`, `STOP`, or unknown values are rejected. UI localization changes display text only and maps deliberately to a canonical enum value before command construction.

### 3.2 Enum versus lookup table

Two common designs were considered:

| Approach | Strengths | Weaknesses |
|---|---|---|
| Lookup table with foreign key | Can attach metadata/display names and add codes through data changes | Suggests Event types are configurable; permits accidental expansion outside approved code/state-machine deployment; adds join and migration surface |
| Closed application enum plus database CHECK | Matches fixed business vocabulary; simple reads; database rejects unknown codes; code and state machine remain exhaustive | Changing vocabulary requires coordinated application/schema migration |

**Selected approach:** closed application enum/value object plus an `Events.EventType` database `CHECK`. The EventAudit `ActionType` uses the same closed-code principle for `ADD`, `EDIT`, `DELETE`.

This choice reflects the rule that Event types are fixed, not user-configurable reference data. A new Event type would change state transitions, runtime behavior, validation messages, tests, schema constraints, and report semantics; it must therefore be an explicit versioned release rather than a lookup-table insertion.

## 4. Date and time storage design

### 4.1 Persian operating date

`EventDate` is an `INTEGER` encoded as Persian `yyyyMMdd`, for example `14050531`. It follows the existing RahNegar convention while gaining strict application validation.

Database structural checks require an eight-digit supported-range value and month component `01..12`; simple day bounds may also reject values outside `01..31`. These checks cannot establish leap-year validity or month-specific Persian day counts. The centralized Persian-calendar domain service must validate:

- actual Persian year/month/day validity;
- correct Esfand length for leap/non-leap years;
- supported application year range;
- not before the Unit baseline/data-start boundary;
- sequential operating-day eligibility;
- finalized Persian month protection.

Invalid dates are rejected. They are never normalized to another day or interpreted through the host culture.

### 4.2 EventTime representation comparison

| Option | Advantages | Risks/costs |
|---|---|---|
| Canonical `TEXT` `HH:mm` | Human-readable in raw queries; lexical sorting works when strictly canonical; familiar legacy shape | Requires careful length/digit/colon/range checks; arithmetic needs parsing; malformed legacy values are a known risk |
| `INTEGER` minute-of-day `0..1439` | Exact minute precision; compact; trivial range check, comparison, and arithmetic; cannot contain seconds or formatting variants | Raw queries require display formatting; `07:05` is stored as `425` rather than visually recognizable text |

**Selected approach:** `INTEGER` minute-of-day. The UI/domain formats it as two-digit `HH:mm`; database and business logic never parse arbitrary time strings after the input boundary. This eliminates legacy variants such as `8:5`, `08:05:30`, and invalid strings that were previously coerced to midnight.

### 4.3 EventDateTime representation

`EventDateTime` is an `INTEGER` canonical chronological minute key derived from the local Persian EventDate and EventTime. The recommended key is a documented epoch-minute value calculated by converting the Persian date to its corresponding Gregorian local calendar date and adding minute-of-day. Its epoch and local-time convention must be fixed in the database metadata/specification and never depend on the current machine culture.

The Event timestamp represents an operating-wall-clock minute, not `CreatedAt`. It has no seconds. The application must avoid applying a current UTC offset to historical/future operating timestamps; the selected conversion is a deterministic calendar chronology for the station's local operating time. `CreatedAt`, UpdatedAt, audit Timestamp, and deletion timestamps remain UTC instants.

### 4.4 Consistency and sorting

- Chain order is `ORDER BY EventDateTime, EventId` for deterministic diagnostics. Active same-Unit ties cannot exist because of the unique constraint.
- Station grids use `ORDER BY EventDateTime, UnitId, EventId` or configured Unit display order after retrieval.
- EventDateTime is recomputed, never trusted from UI or import input.
- EventTime must equal the minute-within-day component encoded by EventDateTime under the documented epoch convention.
- Integrity tooling converts EventDate to Gregorian day, combines EventTime, and compares the result to EventDateTime.

### 4.5 Midnight and Persian boundaries

An Event at EventTime `0` belongs to EventDate at `00:00`. EventTime `1439` is `23:59`. The next minute belongs to the next valid Persian date, obtained through Persian-calendar addition rather than numeric `yyyyMMdd + 1`.

Sorting across Persian month/year boundaries works because EventDateTime is a continuous chronological minute key. EventDate remains available for exact Persian-day and finalized-month queries. Runtime uses half-open operating days `[00:00, next 00:00)`: a run ending exactly at midnight does not create physical overlap on the new day.

## 5. EventAudit table design

### 5.1 Table purpose

`EventAudit` is the immutable history of successful Event mutations. It records the committed canonical before/after snapshots, actor, time, and reason. It is not a general exception log and does not record a successful mutation when a command is rejected or rolled back.

### 5.2 Complete field specification

| Name | SQLite data type | Nullability/default | Constraints | Purpose and lifecycle |
|---|---|---|---|---|
| `AuditId` | `TEXT` | Required; application-generated ULID | Primary key; canonical ULID; immutable | Stable identity for one accepted mutation record. Created once in the Event transaction. |
| `EventId` | `TEXT` | Required; copied from target Event | Foreign key to retained `Events(EventId)` with restrictive/no cascade behavior | Links all ADD/EDIT/DELETE history to the stable Event, including after tombstoning. Never changes. |
| `ActionType` | `TEXT` | Required; no default | Exact `ADD`, `EDIT`, or `DELETE` check | Describes the accepted command. Immutable. |
| `OldValue` | `TEXT` | Nullable | Valid versioned canonical JSON by application contract; action-shape check | Null for ADD; required for EDIT and DELETE. Complete pre-mutation Event snapshot. |
| `NewValue` | `TEXT` | Nullable | Valid versioned canonical JSON by application contract; action-shape check | Required for ADD and EDIT; null for DELETE. Complete post-mutation Event snapshot. |
| `User` | `TEXT` | Required | Nonempty; logical user reference/snapshot policy | Trusted actor who committed the mutation. The logical name is retained to match domain language; a physical implementation may use `UserId` to avoid ambiguity/reserved-word concerns. |
| `Timestamp` | `TEXT` | Required; trusted UTC clock | Canonical UTC ISO-8601; immutable | Commit time of the mutation. |
| `Reason` | `TEXT` | Required by selected policy | Nonempty for EDIT/DELETE; bounded Unicode; no silent truncation | Human explanation. ADD may use a standard reason such as initial entry or a supplied operator reason. |

Snapshots use canonical, versioned JSON with stable field names and formatting policy. They contain business fields, deletion/concurrency state where relevant, and a `SchemaVersion` marker. They do not contain secrets. SQLite JSON validity checks may be used where the deployed SQLite build guarantees JSON functions, but the application serializer remains authoritative for schema/version semantics.

### 5.3 Action-specific rules

| Action | OldValue | NewValue | Event row effect |
|---|---|---|---|
| `ADD` | NULL | Required canonical active Event | Inserts active Events row. |
| `EDIT` | Required prior snapshot | Required updated active snapshot | Updates editable fields, UpdatedAt, and RowVersion; EventId/Station/creation fields unchanged. |
| `DELETE` | Required active prior snapshot | NULL | Marks Events row tombstoned and sets deletion metadata/RowVersion. |

Action-shape checks should enforce these null combinations. The command writes the Event row and exactly one matching audit row in the same transaction. A failure writing either rolls back both.

### 5.4 Append-only behavior and retention

Normal application roles/routes can INSERT EventAudit rows only through the Event command handler. UPDATE and DELETE are prohibited by repository/API design. SQLite has no full user/role security model within a local file, so append-only behavior is reinforced by encapsulation, optional protective triggers, file permissions, integrity checks, backups, and signed/checksummed audit exports where required.

Because the selected Event deletion strategy retains a tombstoned Events row, EventAudit retains a normal foreign key after deletion. There is no `ON DELETE CASCADE`. Physical purge of either Event or audit history is outside normal operation and requires a separately approved retention process that preserves legal/operational traceability and finalized reports.

## 6. Relationships

### 6.1 Events to Station

`Events.StationId -> Stations.StationId` is required with restrictive update/delete behavior. StationId is immutable on Event. A Station that has Events cannot be physically deleted through normal operations; it should be deactivated/retired. This prevents Rasht, Ramsar, or future Station data from being mixed.

Every Event query and command is scoped by StationId from trusted application context. The UI-supplied Station value is not accepted as authorization. Reports select Station explicitly and never infer it from the active database alone in the generalized design.

### 6.2 Events to Unit

The strongest selected ownership relationship is composite:

```text
Events(StationId, UnitId) -> Units(StationId, UnitId)
```

The Units table therefore exposes a unique composite candidate key even if UnitId is globally unique. This makes cross-Station assignment structurally impossible. UnitId is required and cannot reference a retired/nonexistent Unit at the application validation date.

Static ownership is protected by the composite foreign key. Temporal rules—whether the Unit was active or configured for that Station on EventDate—are validated by the command handler because ordinary SQLite foreign keys cannot express “valid during this date interval.” Unit reassignment through Edit validates both complete chains.

### 6.3 EventAudit to Event

`EventAudit.EventId -> Events.EventId` uses restrictive/no-action semantics. Tombstoning preserves the parent, so DELETE audit remains referentially valid. Audit rows cannot be cascade-deleted. A future physical purge must be an explicit archival workflow, not normal Event deletion.

### 6.4 Trusted Runtime Baseline relationship

Although not one of the three requested direct relationships, chain validation depends on a required Trusted Runtime Baseline per Station/Unit. Its schema must use the same composite Station/Unit ownership and an effective boundary. An Event before that boundary is invalid. The database may enforce a simple lower-bound only if the baseline is immutable and expressible through triggers; the authoritative command handler always enforces it during full-chain replay.

## 7. Index strategy

Index names are illustrative logical names; final names follow project conventions. Redundant indexes must be removed during physical design review because a unique composite index can also serve prefix queries.

| Required index/constraint | Shape | Reason |
|---|---|---|
| Event primary key | Unique primary key on `Events(EventId)` | Stable point lookup for Edit/Delete/audit/report references. SQLite automatically indexes the primary key implementation. |
| Active Unit + EventDateTime uniqueness | Unique partial index on `Events(UnitId, EventDateTime) WHERE IsDeleted = 0` when UnitId is global; otherwise include StationId | Guarantees no two active Events for the same Unit share a minute. Tombstoned history does not block a corrected replacement Event. Different Units may share a timestamp. |
| Station + EventDateTime | Non-unique `Events(StationId, EventDateTime)` filtered or beginning with IsDeleted according to query plan | Supports station chronological grid, reports, date ranges, and deterministic Event log loading. |
| Unit + EventDateTime | Non-unique/covering `Events(UnitId, EventDateTime)` for active chain reads | Supports complete Unit-chain reconstruction from baseline and runtime projection. If the partial unique index fully serves active queries, add only a history-inclusive variant when justified by measured plans. |
| EventDate + Station | Non-unique `Events(EventDate, StationId)` or `Events(StationId, EventDate)` selected from dominant query shape | Supports Persian operating-day loads, sequential-day checks, finalized-month impact analysis, and migration reconciliation. Station-first is preferable for strongly Station-scoped queries; the final order must be validated with query plans. |
| EventAudit by Event | Non-unique `EventAudit(EventId, Timestamp)` | Retrieves complete audit history for one Event in commit order. |
| EventAudit by time/user | Non-unique `EventAudit(Timestamp)` and, only if required, `EventAudit(User, Timestamp)` | Supports operational audit review and actor/time investigations. Avoid unused indexes. |

Every query specifies an `ORDER BY`; no caller relies on SQLite return order, rowid, or insertion order. `EventId` is a deterministic final display tie-breaker across different Units or audit diagnostics, never a way to resolve a forbidden same-Unit timestamp tie.

## 8. Database constraints

### 8.1 Required structural integrity rules

1. `EventId` is unique, required, canonical, and immutable.
2. `StationId` is required and references a valid Station.
3. `(StationId, UnitId)` is required and references a Unit owned by that Station.
4. `EventType` is exactly START, NSD, ESD, or OH.
5. `EventDate` has canonical eight-digit Persian shape and plausible components; full calendar validity is enforced by the domain service and verified by integrity scans.
6. `EventTime` is an integer from 0 through 1439, guaranteeing minute precision.
7. `EventDateTime` is required, canonical, and generated from EventDate/EventTime by the command boundary.
8. No two active Events for the same Unit may share EventDateTime.
9. Different Units may have the same EventDateTime; no Station-wide timestamp uniqueness is created.
10. CreatedAt/CreatedBy are required and immutable; UpdatedAt is null until an Edit and cannot precede CreatedAt.
11. Tombstone metadata is internally consistent: active means DeletedAt/DeletedBy null; deleted means both populated.
12. RowVersion is positive and advances on mutation.
13. Audit ActionType and OldValue/NewValue nullability match ADD/EDIT/DELETE semantics.
14. Audit rows never cascade-delete.

### 8.2 Rules intentionally not represented as row CHECK constraints

The database cannot determine from one row whether START, NSD, ESD, or OH is valid in the complete historical state chain. It also cannot reliably express:

- the three-state transition machine;
- the effect of editing/deleting an earlier Event on all later Events;
- sequential daily-entry eligibility across Persian dates;
- a Unit's temporal configuration validity;
- Trusted Runtime Baseline state and effective boundary semantics;
- ESD adjustment eligibility;
- finalized-month policy without cross-table triggers.

These rules are enforced by the domain/application command handler inside the same transaction as mutation. Database constraints are defense in depth: they protect shape, ownership, uniqueness, and races, but they never replace complete-chain validation or clear Persian correction messages.

## 9. SQLite implementation considerations

### 9.1 Foreign-key enforcement

SQLite foreign keys must be enabled on every opened connection with `PRAGMA foreign_keys = ON`; setting it once during schema creation is insufficient. Connection factory tests must prove enforcement for normal commands, reports, migration tools, backups/restores, and maintenance utilities. Foreign-key failures are translated to structured application errors and roll back the transaction.

Parent key definitions must match child affinity/collation exactly, especially for TEXT ULIDs and composite `(StationId, UnitId)` keys. Parent updates/deletes use RESTRICT/NO ACTION. Cascades are not used for Event or audit history.

### 9.2 Transaction behavior and concurrency

SQLite allows one writer at a time but does not make validation on a prior connection safe. Each command begins a write transaction suitable for acquiring the necessary writer reservation before reading baseline/chains, then performs validation and mutation on that connection. The exact `DEFERRED` versus `IMMEDIATE` choice must be load-tested; `IMMEDIATE` is favored for short mutation commands because it exposes write contention before expensive full-chain validation and prevents two writers from validating stale state before competing to commit.

WAL mode and busy timeout may improve desktop responsiveness, but correctness does not depend on them. Transactions remain short: no MessageBox, user confirmation, network call, or long report generation occurs while the transaction is open. The UI gathers confirmation/reason first, then submits the command.

`RowVersion` provides stale-editor detection. The update/tombstone statement matches EventId plus expected RowVersion and must affect exactly one active row. A zero-row result is a concurrency conflict and causes rollback/reload guidance.

### 9.3 Constraint and trigger limitations

- SQLite dynamic typing requires explicit type/shape checks; declared types alone do not prevent incompatible storage classes unless STRICT tables are selected and supported by the deployed SQLite version.
- Persian calendar validity is not natively available.
- Cross-table and temporal ownership rules cannot be represented by ordinary foreign keys.
- CHECK constraints cannot replay Event chains.
- Partial unique indexes are appropriate for active tombstones but require confirmed runtime SQLite support.
- Triggers can protect append-only audit or immutable fields, but complex business state logic must not be duplicated in triggers. Duplicate implementations would drift and yield poor user messages.

The physical design should use STRICT tables if the supported bundled SQLite version and compatibility testing permit it. This is a reviewed implementation choice, not permission to upgrade packages or migrate current production schema.

### 9.4 Migration mechanics

SQLite schema changes often require creating a new table, copying validated data, recreating indexes/foreign keys, and swapping names. That implementation pattern is potentially destructive if interrupted or applied to bad data. It must be designed separately with backup, verification, foreign-key checks, row counts, audit/provenance, rollback, and explicit approval. This document creates no migration.

### 10.1 Mapping table

| None | `UpdatedAt` | NULL for imported canonical row unless verified update metadata exists | Must not invent edit time | Legacy update history is absent. |
| Migration default | `IsDeleted` | `0` only for approved active imports | Full chain valid and duplicate-free | Legacy deleted Events are irrecoverable from current table. |
| None | `DeletedAt`, `DeletedBy` | NULL | Tombstone consistency | No legacy delete provenance exists. |
| Migration default | `RowVersion` | `1` | Positive | Does not represent unknown legacy edit count. |

### 10.2 Required migration validation

Migration operates through staging and reports; it does not insert directly into constrained production tables until reviewed data passes:

1. Inventory every row with source database fingerprint and legacy id.
2. Validate Station mapping, Unit ownership, canonical type, Persian date, and exact minute time.
3. Detect duplicate canonical `(Station, Unit, EventDateTime)` before creating/enabling the unique index.
4. Replay each complete Unit chain from its Trusted Runtime Baseline and report every forbidden transition.
5. Identify finalized-period rows and preserve their connection to legacy snapshots/calculation behavior.
6. Generate a review queue for every ambiguity; never auto-delete, merge, retime, invent START/shutdown, or rewrite meaning.
7. Import only approved rows, generate stable ids and migration provenance, rerun complete validation, then verify constraints/foreign keys/counts.

No destructive migration is authorized. Invalid legacy data requires business review and a documented disposition. Constraint creation must occur only after duplicate and integrity remediation; otherwise the migration should stop safely and leave source data unchanged.

## 11. Event deletion strategy

### 11.1 Option comparison

| Criterion | Option A: Hard delete + retained audit | Option B: Soft delete/tombstone |
|---|---|---|
| Active chain simplicity | Active table contains only current Events | Every active query must filter IsDeleted = 0 |
| Audit foreign key | Difficult: hard deletion breaks a normal required FK, requiring weak/no FK, archival parent, or special deferred design | Strong FK remains valid because Event row is retained |
| Stable identity after delete | Exists only in audit snapshot | Parent identity and deletion metadata remain queryable |
| Accidental omission risk | Lower for active queries | Higher if a query forgets active filter; mitigated by repository/view conventions and partial indexes |
| Database growth | Smaller Events table | Retains deleted rows; expected Event volume is small enough for desktop SQLite |
| Timestamp reuse | Unique constraint naturally frees timestamp | Requires partial unique index over active rows |
| Forensic clarity | Requires joining/decoding audit | Direct tombstone plus audit provides clear provenance |
| Restore potential | Requires reconstruction as a new Event and full validation | Still requires explicit validated restore command, but source row remains available |
| Finalized/report traceability | Depends heavily on audit snapshots | Easier to relate historical identity, audit, and snapshots |

### 11.2 Selected approach

**Recommendation: Option B, soft delete/tombstone.** Event volume is modest, while stable referential audit history and operational traceability are high-value. DeleteEventCommand validates the chain after removing the Event from the active set, then atomically sets IsDeleted/DeletedAt/DeletedBy, increments RowVersion, and inserts a DELETE audit row.

All authoritative chain and runtime queries use active rows only through a single repository/query abstraction or an explicitly defined active-Events view. A partial unique index enforces Unit/EventDateTime uniqueness for active rows. Raw query review and integration tests must catch missing tombstone predicates.

Tombstoning does not make restore automatic. A restore would reintroduce a state transition and might invalidate later Events, so it requires a future explicit RestoreEventCommand, full-chain replay, duplicate checks, lock checks, and a new audit action approved by architecture. Until then, correction after deletion is performed by a new Add with a new EventId, while the deleted Event remains historical evidence.

## 12. Versioning and finalized reports

Finalized reports are immutable snapshots, not live reinterpretations of mutable Event rows. The finalization transaction must bind together:

- Station and Persian reporting period;
- report snapshot data;
- Event/runtime calculation version;
- ESD adjustment/settings version and value;
- Trusted Runtime Baseline version/effective boundary;
- a consistent Event dataset marker, such as maximum committed audit sequence/timestamp plus database snapshot identity or a calculated Event-set hash;
- finalization actor and UTC timestamp;
- finalized-month lock.

An Event command may not Add/Edit/Delete an Event in a finalized month. An Edit moving an Event across months checks both the old and new month. Because an earlier Event can affect runtime in later periods, finalization policy must additionally define cross-period dependency handling: once a month is finalized, edits to an earlier unlocked month that would change state/runtime flowing into a locked later month must be rejected or handled by an explicit reopening/re-finalization governance process. The safe default is rejection until every affected finalized snapshot is explicitly reopened under authorization.

Calculation versions are stored with snapshots, not inferred from application version. A new runtime engine does not silently recalculate old finalized reports. Live analytical views may use the current version but must label differences from locked snapshots. Migration reconciliation retains legacy calculation provenance and never overwrites a finalized snapshot merely because corrected logic produces a different number.

Snapshot creation and lock insertion occur in one transaction using the same consistent Event/baseline/settings view. If snapshot persistence or lock creation fails, neither is committed.

## 13. Security and ownership

### 13.1 Actor fields

- `CreatedBy` is required and immutable, sourced from trusted authenticated application context rather than an editable UI field.
- `EventAudit.User` records the actor for every Add/Edit/Delete and is the authoritative editor/deleter history.
- A separate `UpdatedBy` column on Events is **not selected** for the minimum schema because it duplicates the latest EDIT EventAudit actor and can drift. `UpdatedAt` plus RowVersion supports concurrency, while audit supplies actor/reason. If read-performance requirements later justify denormalizing UpdatedBy, it must be maintained atomically and verified against the latest EDIT audit.
- `DeletedBy` is retained on the tombstone for direct deletion status and must match the DELETE audit actor.

### 13.2 Authorization boundary

Authorization is enforced in the Event command handler before validation/mutation and inside the transaction where relevant. The handler verifies:

- current user may access Station;
- Unit belongs to Station;
- user has Add/Edit/Delete permission;
- Edit cannot transfer Station;
- finalized periods cannot be changed without a separately approved reopen workflow;
- migration identity is limited to controlled migration operations.

UI visibility/enabled state is not authorization. Repository methods are internal and require an established transaction/command context. Imports, test seeders, and maintenance utilities cannot write Events directly.

### 13.3 Preventing direct database bypass

An offline SQLite file cannot provide server-grade access control against a user/process with filesystem write access. The architecture therefore uses layered controls:

- least-privilege filesystem permissions for the data directory;
- application-only mutation APIs and no production raw Event editor;
- foreign keys, checks, and unique indexes;
- optional triggers protecting immutable columns and append-only audit behavior;
- database integrity/foreign-key checks at maintenance boundaries;
- encrypted/signed backup strategy where required by broader platform policy;
- audit reconciliation and Event-chain verification to detect tampering;
- no cloud or external authentication dependency.

These measures reduce accidental and application-level bypass. They cannot claim cryptographic non-repudiation against a local administrator who can replace the database and application binaries. Any stronger threat model requires a separately approved security architecture.

## 14. Final schema decision table

| Decision | Selected approach | Reason | Implementation impact |
|---|---|---|---|
| Event table | New `Events` table; do not reuse `tbl_events` directly | Legacy table lacks stable application identity, Station ownership, constraints, and audit | Controlled staged migration; legacy remains unchanged until approved cutover |
| Event identity | Application-generated canonical ULID in TEXT primary key | Stable across offline databases/migrations and known before insert | Shared generator/parser; no rowid as business identity |
| Station isolation | Required StationId FK plus composite Station/Unit ownership FK | Prevents Rasht/Ramsar/future Station leakage | Units expose unique `(StationId, UnitId)` key; every query is Station-scoped |
| Event type | Uppercase TEXT with closed enum and CHECK | Types are fixed and change state/runtime semantics | Coordinated code/schema release for any future type |
| Persian date | INTEGER `yyyyMMdd` plus application Persian-calendar validation | Preserves RahNegar convention and efficient day/month filtering | Structural CHECK plus centralized full validation |
| Event time | INTEGER minute-of-day `0..1439` | Exact minute precision and simple validation/arithmetic | UI formats HH:mm; migration strictly parses legacy text |
| EventDateTime | Derived INTEGER chronological local epoch-minute key | Deterministic sort, uniqueness, chain scans, and runtime math | Central converter; recompute on write; integrity round-trip scans |
| Timestamp uniqueness | Unique partial active index on UnitId + EventDateTime | Same Unit cannot have two active Events at one minute; different Units can | Clear duplicate precheck plus database race defense |
| Event chronology | Explicit ORDER BY EventDateTime and deterministic secondary keys | SQLite return/rowid order is not authoritative | All repositories/reports specify ordering |
| Remark | Nullable bounded Unicode; reject overflow | Preserves operator context without silent data loss | Product confirms allowed types/maximum before implementation |
| Creation metadata | Immutable CreatedAt UTC and CreatedBy | Establishes origin independent of operational time | Trusted clock/user context; immutable-field protection |
| Edit concurrency | UpdatedAt plus integer RowVersion | Prevents stale overwrites and supports operator feedback | Edit/Delete match expected version and increment atomically |
| Deletion | Soft delete/tombstone | Preserves stable FK/audit/forensic identity at low data-volume cost | Active filters/view, deletion metadata, partial unique index |
| Audit table | Append-only EventAudit with versioned old/new JSON | Complete accepted mutation history | Atomic audit insert; no UPDATE/DELETE/cascade |
| Audit actor | Required logical User field; no minimum Events.UpdatedBy | Audit is authoritative for editor identity and avoids duplicate drift | Latest editor requires audit query; optional denormalization needs later decision |
| Foreign keys | Enforced on every SQLite connection; restrictive deletes | Prevents orphan/cross-owner data | Connection factory/integration tests; no cascades |
| State-machine integrity | Domain command transaction, not trigger/CHECK | Requires complete history and actionable errors | Full affected-chain replay for Add/Edit/Delete |
| Validation transaction | Begin write transaction before baseline/chain read and retain through mutation/audit | Removes validation/mutation race and partial writes | Short transactions; no UI interaction while open |
| Runtime storage | Do not store runtime in Events | Runtime is a versioned projection from baseline and Events | Reporting engine reconstructs full history and separates physical/adjustment |
| Finalized reports | Immutable versioned snapshots tied to consistent Event set and lock | Prevents new logic or later edits silently changing official output | Store calculation/baseline/settings versions and dependency marker |
| Legacy duplicates | Detect and review before unique constraint | Constraint creation would otherwise fail or force data loss | Non-destructive exception report; no automatic merge/delete/retime |
| Invalid legacy rows | Human-reviewed staging exceptions | Original intent cannot safely be guessed | Migration stops affected rows/chains pending documented disposition |
| SQLite STRICT/triggers | Consider after compatibility review; use triggers only for structural protection | Useful defense, but must not duplicate state-machine business logic | Version/runtime compatibility tests before schema implementation |
| Direct database security | Layered constraints, encapsulation, filesystem controls, integrity checks | SQLite file has no server-grade role boundary | Explicitly document residual local-administrator threat |
| Destructive migration | Prohibited without explicit review and rollback plan | Protects user history and finalized reports | This specification creates no SQL or migration |
